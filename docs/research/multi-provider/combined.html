Implementation research / Observer config TUI

Employee models across five coding CLIs

A design for assigning every roster employee a model and reasoning configuration per host profile. The TUI can list and save all five providers now. Applying that choice to a delegated child remains capability-gated, because discovery and control are different problems.

Decision

Build a host-adapter registry. Keep roster matching, skills, desired-versus-observed state, and the pure TUI above it. Put model discovery, option vocabularies, profile identity, validation, installation, pre-spawn control, and restart rules in one adapter per CLI.
Opaque
model IDs

The shared schema accepts a non-empty host-owned string. OpenCode alone enforces provider/model.

Typed
model options

Selections are string or boolean values keyed by an adapter-owned option ID.

Explicit
control state

The TUI says supported, experimental, unavailable, or inactive for each target.

In Observer's own vocabulary, these CLIs are hosts. T3 calls them providers. OpenCode also has upstream providers inside one host. The implementation must retain that distinction or an ID such as anthropic/claude-opus-4-8 will be mistaken for an OpenCode profile.

Proposed seat schema

An employee has shared skills and zero or more host targets. A target points at a host profile, stores an opaque model ID, and carries typed host options. The target's profile selects the binary, config directory, endpoint, or account context. Credentials remain in the host or secret store, never in the employee seat.

Migration of shipped OpenCode seats

Current model and variant fields are persisted and documented, so there is a concrete compatibility need. On load, treat them as a legacy opencode:default target. On the first TUI save, write the target shape and remove only those two promoted fields. Preserve all unrelated unknown fields exactly as the current schema does.

Host adapter contract

The contract separates model catalog, validation, observation, and child control. A provider can implement one without pretending it implements the others.

type HostKind = "codex" | "claude" | "cursor" | "grok" | "opencode"
type OptionValue = string | boolean

interface HostSeatAdapter {
  kind: HostKind
  label: string
  profiles(): HostProfile[]
  catalogue(profileId: string): ModelCatalogue
  diagnose(profileId: string, target: SeatTarget): SeatFinding[]
  capabilities(profileId: string): {
    discovery: "live" | "cached" | "manual"
    childModel: "supported" | "experimental" | "unsupported"
    childReasoning: "supported" | "experimental" | "unsupported"
    requiresReload: boolean
  }
  reconcile?(profileId: string, seats: SeatsConfig): ReconcileResult
}

interface ModelCatalogue {
  models: Array<{
    id: string
    label: string
    contextWindow?: number
    options: ModelOptionDescriptor[]
  }>
  source: string
  freshness: "live" | "cached" | "unknown"
  warnings: string[]
}

Shared code owns

Roster IDs, employee skills, target persistence, string/boolean option values, dirty/save behavior, generic severity, configured versus observed distinction, and fail-open policy.

Adapter owns

Profile discovery, CLI/API calls, model ID grammar, option descriptors, capability checks, generated files, hook mutations, runtime registry checks, restart instructions, and host-specific diagnostics.

One global seats.control can remain the master consent switch. An adapter capability determines whether that consent can be acted on. Future per-target control flags are only needed if users ask to enable control for one host and disable it for another.

Configured is not observed

The seat is what the user wants. The agent entity is what the host reported. Multi-provider reasoning requires the same separation already used for model attribution.

desired target
  model: "gpt-5.6-sol"
  options: [{ id: "reasoningEffort", value: "high" }]

observed agent
  model: "gpt-5.6-sol"
  modelConfidence: "authoritative"
  effort: "high"              // only if host emitted it
  effortConfidence: "reconciled"
  controlOutcome: "applied" | "declined" | "unknown"
  • Never copy desired effort into an observed agent record.
  • Registry presence, a successful file write, or a sent model request proves only that Observer attempted control.
  • Hosts that cannot report effective effort remain unknown, even when control likely succeeded.
  • A child model reported by the host can be authoritative while its parent edge is reconciled. Keep provenance per fact.

Tracer-bullet delivery

  1. Define contracts. Add target records, typed options, host/profile IDs, adapter capability results, and migration tests for existing OpenCode seats.
  2. Extract OpenCode. Move today's catalog, diagnostics, agent reconciliation, and plugin control behind the first adapter without changing behavior.
  3. Generalize the TUI. Add host-target and dynamic-option views. Prove all 14 employees appear and non-TTY reports remain complete.
  4. Add discovery adapters. Implement Codex, Claude, Cursor, and Grok inventories with timeouts, cache/freshness metadata, custom model preservation, and profile isolation.
  5. Ship honest configuration. Users can configure all five hosts. OpenCode applies; the others display experimental or unsupported control state exactly as the matrix says.
  6. Prototype Codex control. Capture real spawn fixtures, implement synchronous fail-open mutation, and add integration tests before changing the capability to supported.
  7. Prototype Claude control. Verify profile-local generated definitions, neutral Agent detection, effort/version behavior, and failure fallback.
  8. Wait for contracts. Add Cursor or Grok child control only after the host exposes a stable per-child operation and Observer has real fixtures.

Verification plan

Shared contract tests

  • Every roster employee appears once and in roster order.
  • Legacy OpenCode seats migrate without losing unknown fields.
  • Opaque bare model IDs survive parsing and saving.
  • String and boolean options round-trip.
  • Unsupported control is visible and never counted as effective.

Adapter contract suite

  • Missing CLI, timeout, malformed output, stale cache, and auth uncertainty.
  • Model accepted, custom model retained, option exact/none/unknown.
  • Profile mismatch and multiple profiles of one host.
  • Control unsupported, declined, registry stale, and host rejection.
  • Every mutation failure preserves the original delegation.

TUI tests

  • Employee to target to model to option navigation and escape unwinding.
  • Dependent option clearing on model change.
  • Viewport scrolling with 14 employees and large catalogs.
  • Plain output contains no ANSI and lists unsupported targets.
  • Save applies adapters independently and reports partial failures.

Host fixtures

  • Codex app-server model pages and child spawn hook payloads.
  • Claude model/profile variants and Agent hook input/output.
  • Cursor grouped ACP options and post-model refresh.
  • Grok empty options, model request optimism, and future private child events.
  • OpenCode nested provider/model IDs and generated-agent registry drift.
