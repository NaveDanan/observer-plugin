OpenCode

OpenCode is the only provider Observer controls today. The mechanism is safe because it is narrow: a generated hidden agent replaces only general, only after the running host confirms the agent exists. This implementation should become the first provider adapter, not the generic contract.

Two provider dimensions

A T3 OpenCode instance is a configured runtime. Inside it, OpenCode connects to upstream provider IDs such as openai, anthropic, or openrouter. A model slug such as openrouter/qwen/qwen3-coder belongs to the OpenCode instance; it does not identify the T3 account or config root.

Observer currently assumes one global OpenCode config root. Multi-instance support requires explicit config roots or instance-qualified generated names. Otherwise two profiles can demand different models for the same generated employee name.

Catalog and reasoning

  1. Observer first reads OpenCode's models.dev cache and narrows it using credential file key names. Values and tokens are never read.
  2. Configured seat models are pinned so a stale credential filter cannot hide an existing choice.
  3. An optional opencode models --verbose probe supplies the host's actual available IDs and resolved variants map.
  4. The host map overrides inference. A variant map is the same data OpenCode validates at delegation time.

Exact efforts

The host or catalog publishes a non-empty ordered effort menu. Offer exactly those values.

No effort

The model has no reasoning mechanism or the host resolves an empty variant map. Offer no control.

Unknown

Model metadata cannot determine OpenCode's synthesized variants. Offer suggestions but label them as unverified.

Current child-control mechanism

seats.employees.arjun-mehta
  -> observer install opencode
  -> agent/observer-arjun-mehta.md
  -> plugin tool.execute.before
  -> subagent_type: general -> observer-arjun-mehta
  -> OpenCode task tool resolves the loaded agent definition
  • The generated definition has mode: subagent, hidden: true, the selected model and variant, an empty body, and todowrite: deny to match general.
  • The plugin appends the employee directive to the task prompt. The generated file contains no duplicate or stale persona.
  • The plugin asks client.app.agents() before rewriting. A file on disk is not enough because OpenCode loads definitions at startup.
  • Missing host, missing registry entry, unsupported original agent, disabled control, and other uncertainty all preserve the original task.
Registry presence is not effective-model proof. Observer should continue to read the child model from OpenCode message metadata. It still cannot observe the child's effective variant, so configured effort must not be displayed as observed fact.

What belongs in the OpenCode adapter

Discovery

Cache paths, auth-key filtering, opencode models, server inventory, provider/model parsing, nested slash handling, context/release metadata, and variant inference.

Control

Agent file format, config root, marker ownership, generated names, neutral-agent policy, permission parity, host registry lookup, rewrite, restart requirement, and cleanup.

Validation

The slash rule, variant-with-model requirement, exact variant rejection, unknown variant tolerance, and configured-model diagnostics.

Observation

parentID, child session joining, message model IDs, task completion fallback, event ignore list, and host-specific provenance.

The shared layer should own roster IDs, employee skills, desired versus observed separation, generic option values, diagnostics severity, and fail-open policy. It should not know how an OpenCode agent file works.

Observer migration notes

  1. Freeze current OpenCode behavior with adapter-level catalog, generated-file, plugin, and TUI tests.
  2. Introduce the provider adapter contract, then move the existing code behind it without changing persisted behavior.
  3. Add a target/profile dimension to employee seats. Migrate the existing top-level model/variant fields as a legacy OpenCode target because this config has shipped.
  4. Honor OPENCODE_CONFIG_DIR and make multiple OpenCode profiles explicit before claiming multi-instance support.
  5. Keep model IDs opaque in shared code. Apply the slash grammar only in the OpenCode adapter.
  6. Add observed effort only when OpenCode exposes it. Until then, show configured effort as requested and observed effort as unknown.
